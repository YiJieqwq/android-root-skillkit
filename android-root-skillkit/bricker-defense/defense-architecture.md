# 通用格机防御架构

## 1. 全天候防格架构

### 1.1 资产注册表

为每个受保护资产保存持久身份、当前运行时身份和策略，例如：

- 持久身份：GPT PARTUUID/分区 GUID、分区名与槽位、DM UUID/逻辑分区元数据、底层设备身份；
- 当前运行时身份：解析后的 `dev_t`、gendisk/partition 与 Device Mapper 映射链；
- 经当前映射验证的必要 LBA 范围；
- 当前可信摘要；
- 恢复镜像或恢复材料；
- 允许的维护主体和操作；
- 资产风险等级。

避免只保存路径；路径可能变化、存在别名或被重新创建。`dev_t` 适合在当前启动会话中归一化对象，但 DM minor、snapshot 和逻辑分区映射可能在重启或 OTA 后变化；每次启动、OTA 和维护窗口退出后都应重新解析并验证持久身份与运行时身份的绑定。

### 1.2 打开阶段守卫

对未授权主体：

- 允许必要的只读访问；
- 拒绝以写、读写或可产生修改的方式打开受保护块设备；
- 对已知系统服务使用明确白名单或能力授权，而非宽泛 UID 0 信任。

优点：简单、早拦截、性能成本低。

遗漏：继承/传递 FD、mmap、内核直接 I/O、Binder 代写和已打开句柄。

### 1.3 操作阶段守卫

覆盖受保护对象上的：

- write/pwrite/writev；
- truncate/fallocate；
- 危险 block ioctl；
- 可写 MAP_SHARED；
- Device Mapper 重映射；
- 刷新/提交相关异常路径。

策略应基于对象身份和授权，不基于用户传入路径。

### 1.4 最终落点兜底

对少量最高价值启动链资产，可在接近 block/BIO 的位置验证最终落点，即使进程归因丢失也不允许写入。

风险：

- 低层 Hook 稳定性要求极高；
- 容易阻断合法 OTA/恢复；
- 内核版本漂移；
- 错误实现可能 panic 或损坏 I/O。

因此只应用于有限关键资产，并配合 monitor-only、维护窗口和虚拟块设备测试。

### 1.5 维护窗口

合法 OTA、刷机、校准和恢复必须通过受认证维护能力：

- 按范围授权；
- 短时有效；
- 绑定当前启动；
- 自动超时；
- 重启不持久；
- 记录进入、操作和退出；
- 高风险分析会话期间拒绝开启。

### 1.6 完整性与恢复

- 定期/事件触发验证关键资产；
- 保护恢复包、映射和 Hash；
- RAM 缓存只读化并检测篡改；
- 提供外部离线备份；
- 恢复动作必须二次验证目标和镜像；
- 明确只提供“内核仍存活时的恢复机会”。

## 2. 针对性分析架构

### 2.1 会话建立

- 预检目标；
- 在目标执行前注册；
- 分配 session；
- 开启围堵后再释放目标；
- 追踪 fork/clone/exec/exit；
- 活跃后代归零后才解除；
- 防止两个高风险会话混用策略和证据。

### 2.2 操作策略与事件枚举

三个维度必须分开记录：

```text
PolicyMode      = TRACE | AUTO | STRICT | EXPERT
Decision        = PASS | SIMULATE | SUPPRESS | ALERT | VERIFY | RECOVER
ExecutionResult = SUCCESS | DENIED | EMULATED | FAILED | UNKNOWN
```

针对目标和派生行为：

- TRACE：记录但尽量不干预，适合已知安全目标；
- AUTO：危险操作模拟成功，适合初次分析；
- STRICT：更广泛拒绝模块加载、持久化、网络和间接 I/O；
- EXPERT：人工设置断点、规则和单步策略。

### 2.3 进程到对象/请求的溯源

逐步维护：

```text
进程 session
→ FD/file/inode
→ mmap/VMA
→ io_uring request
→ Binder transaction
→ writeback/BIO
```

目标是把异步 worker 或系统服务的最终操作关联回原始分析目标。

### 2.4 模拟成功与 Shadow Readback

初级模拟：吞掉危险写入并返回成功。

高级模拟：维护受限影子写集，使目标之后读取同一区域时看到逻辑上已经写入的数据，真实资产不变。

必须限制：

- 仅分析会话；
- 仅明确目标和范围；
- 有容量上限；
- 有溢出/降级记录；
- 不作为通用块虚拟化替代品。

### 2.5 持久化与重启

若想把“重启”作为清场手段，必须先保证：

- 目标未写入 Root 模块目录、启动脚本和 init 配置；
- 未安装 KPM/`.ko`/eBPF；
- 未修改 boot-chain；
- 重启路径受控；
- 系统服务代写也被归因或关键资产兜底。

否则重启可能触发第二阶段载荷，而不是清场。

### 2.6 证据

事件至少包含：

- 单调时钟和 UTC；
- session、PID/TGID、UID、进程和血统；
- 真实资产/设备身份；
- 操作类型、范围、结果和策略动作；
- PolicyMode、Decision、ExecutionResult 三个独立字段；
- 信任状态；
- 丢事件/溢出计数。

事件环需考虑并发提交、读写撕裂、覆盖和篡改。静默丢事件会使分析结论不可信。

### 2.7 走查示例：自解压 sh + ELF 格机样本

把 2.1–2.6 串成目标架构行为（示例场景，防御视角）。以下不表示单个 Hook 即可实现；影子 FD、Shadow Readback、完整 mmap 虚拟化和异步因果归属属于可选/实验能力，必须通过对应测试验证。未实现一致影子语义时应拒绝危险操作，而不是伪造不一致的成功结果：

1. **预检**：解析可疑 APK，发现 assets 内含自解压 sh（脚本头部 + 内嵌 ELF）；确认目标未启动。
2. **会话建立**：注册 APK 主进程为分析目标，策略 AUTO（危险操作模拟成功），记录信任快照。
3. **释放追踪**：sh 解出 ELF 到 `/data/local/tmp/xxx`、`chmod +x`、`exec` —— 通过 fork/clone/exec 血统把 ELF 归入同一 session；解压与 exec 事件入证据。
4. **打开阶段**：ELF 以 `O_WRONLY` 打开受保护块设备（如 `/dev/block/by-name/userdata`）→ 守卫按 `dev_t` 归一化命中，AUTO 策略下模拟成功（返回正常 FD 但落点兜底拦截），记录事件。
5. **操作阶段**：批量 write/危险 ioctl（discard/zero-out）→ 模拟成功或 SUPPRESS，记录范围与次数；mmap/io_uring 路径由操作阶段守卫覆盖。
6. **副作用**：ELF 看到“写入成功”后继续后续行为——这正是 SIMULATE 的目的：让样本走完完整流程，暴露全部行为。
7. **清场尝试**：样本请求 reboot —— 受控重启路径检查：确认未写 Root 模块目录、启动脚本、KPM/.ko、boot-chain；满足条件才允许走受控重启，否则拒绝。
8. **会话结束**：活跃后代归零 → 解除围堵 → 清理临时资产（`/data/local/tmp` 等）→ 导出证据（时间线、资产、操作、PASS/SIMULATE/SUPPRESS 标记）。
9. **恢复验证**：核对关键资产摘要与恢复材料一致；记录信任状态与溢出计数。

## 3. 内核扩展与自保护

### 3.1 冻结已知入口

分析会话中可观察或禁止：

- Linux 模块加载/卸载；
- KPM 加载；
- eBPF；
- Root 管理器扩展入口。

合法维护应经过独立认证，不能只判断调用者是否 UID 0。

### 3.2 信任快照

会话开始时记录：

- 已加载模块/KPM基线；
- 关键 Hook 摘要；
- 策略状态；
- 资产映射；
- 防御组件版本。

若发生异常变化，将会话标记为 TRUST DEGRADED，并避免继续做过强安全承诺。

### 3.3 控制面

Root 对手可读写普通 procfs/debugfs 节点。控制面应考虑：

- 会话认证和防重放；
- 独占客户端或授权 FD；
- 命令作用域与状态机；
- 登录限速/锁定；
- 回复通道防投毒；
- 分析日志不泄漏到对手可读 dmesg；
- CLI 被杀后围堵保持 fail-closed；
- 控制面失联的安全恢复策略。

“加密”不替代认证；本地 Root 对手场景首先要防命令伪造、投毒和越权。

## 4. 推荐测试矩阵

仅使用 disposable loop/虚拟块设备：

| 类别 | 测试目标 |
|---|---|
| 正常路径 | 合法只读、授权维护、系统服务不被误伤 |
| 直接写 | 普通写、分段写、并发写 |
| ioctl | discard/zero-out 等被识别 |
| mmap | 可写共享映射不能改变 backing file |
| 异步 | io_uring worker 不丢失策略 |
| deputy | 外部服务代写被关键资产兜底或正确归因 |
| FD | 继承、传递、dup 后策略仍有效 |
| 别名 | by-name、mapper、软链接归一到同一对象 |
| 模块 | 未授权内核扩展被观察/冻结 |
| 控制面 | 投毒、重放、并发客户端、CLI 被杀 |
| 证据 | 并发、环覆盖、溢出计数、时间戳 |
| 故障 | Hook 失败回滚、模块卸载、重启、超时维护 |

测试程序必须自行验证目标是专用 loop 设备，任何身份不符都应拒绝执行。

## 5. 产品声明边界

可以说：

- 降低 Root 用户空间格机和已知内核扩展路径的风险；
- 保护指定启动链资产；
- 对注册分析目标提供模拟/阻断和证据；
- 在条件满足时提供 live-kernel 恢复机会。

不要说：

- 绝对无法格机；
- 能阻止任意恶意 KPM/内核漏洞；
- 保证任何硬砖都可恢复；
- 覆盖 RPMB、TEE、EL2、存储固件和物理攻击；
- 分析环境完全不可检测。
